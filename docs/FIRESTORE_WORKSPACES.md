# Clerk and Firestore scene persistence

Set `SCENE_STORE=firestore` after configuring the server-only fields in `.env.example`. The existing `/api/scenes`, `/api/scenes/update`, `/api/scenes/delete` and `/api/scene-context` endpoints then use verified Clerk identity and durable Firestore scene storage. Missing configuration fails closed; no scene is silently saved into Vercel's ephemeral SQLite filesystem. Local legacy mode remains available when the feature flag is absent.

The existing, concurrently updated Clerk identity and billing flow is preserved. Scene requests obtain a current Clerk JWT directly from the SDK; the new scene adapter never writes that JWT into localStorage. Legacy application sessions remain unchanged. User/organization changes select a new namespace; personal Pro does not grant a free organization a paid entitlement. Organization settings use Clerk's own controls. Keep membership optional and preserve the included 20-member configuration. No paid Clerk add-on has been purchased.

Data path: `quantura_web/frontiersight-ai/tenants/{user_USER_ID|org_ORG_ID}/records/{uuid}`. Scene payloads are capped at 256 KiB. GET returns at most ten full scenes per page; follow `next` using `after`. Write requests require a 16–128 character `Idempotency-Key`. Updates and deletes require `expectedVersion`. Only organization admins may delete shared records. All record/counter/audit/receipt changes transact together; no model or billing calls run in retried callbacks. Minute request counters cap per-tenant requests. The browser must not treat a failed update as a successful new create.

This integration does not automatically migrate legacy SQLite scenes/accounts to Clerk. Existing Clerk sync, billing, BYOK and support routes remain intact. Only opted-in scene persistence uses the new server-verified Firestore namespace; accounts and billing still require their existing persistence/lifecycle review. Existing public deterministic physics/MCP tools are not converted into private workspace tools by this storage change. Advanced metered analysis and third-party API usage require separate production enforcement review.

See `packages/enterprise-web/README.md` for server IAM/rules responsibilities, TTL/index candidates, cost bounds, HMAC/rollback limitations, account-erasure limitations and provider prerequisites. Production Firestore metadata confirmed an existing Native-mode default database in `quantura-e2e3d`; published rules could not be read by the current session. No production rules, IAM, database, data, prices or deployments were changed. Before activation, review the published rules for broad allows and grant an appropriately scoped service identity. Do not copy a developer's broad OAuth credentials to Vercel.

Validation is against an isolated `demo-quantura-web` emulator with direct client access denied. Real signed sessions are verified by the official Clerk SDK. `scripts/verify-firestore-emulator.sh` runs both language suites; their coverage artifacts are distinct. React/vanilla-browser execution is not included in the server coverage percentage. Real production payment, account lifecycle and cloud load verification remain required.

Latest local evidence after merging the newer default branch: 96 tests passed. New Python scene/auth modules: 98.29% line coverage and 96.55% branch coverage; committed `coverage/firestore.xml` contains real hit counts. Server coverage excludes browser execution. The concurrent default branch's newer Clerk identity/billing implementation is retained. The integration additionally rejects email-only account linking and predictable Clerk-account password login; sync uses a verified server-side Clerk profile rather than posted email/name.

Security reconciliation: email-only automatic linking was removed, Clerk-managed account password login is blocked, and new Clerk-managed password hashes use random unrecoverable material. Posted email/name is ignored by the sync endpoint; it fetches the verified primary email from Clerk Backend API. Existing same-email accounts require a separately verified owner-linking flow, not automatic merging. Origin authorization is checked before profile sync. These negative cases are covered by regression tests; live provider verification is not claimed.
